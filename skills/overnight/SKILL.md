# Overnight

The goal is a measurably better, observed-working result by morning, not a long activity log.

## Phase 0 - recover state fast

In the first minutes:

1. Create a provisional Codex goal for the overnight objective.
2. Read `~/workspace/ORCHESTRATION-BOARD.md`, the relevant repo instructions, git/runtime state, current task/thread status, and the most relevant native/Claude historical memory.
3. Check for dirty checkouts, active workers, signed-in worker surfaces, current model rosters, and usable plan headroom.
4. Check for code-lane collisions. Do not share an editing checkout.
5. Give Zach a short evidence-backed status: what is done, what is actually running, what is broken, and what decisions matter tonight.

## Phase 1 - brainstorm and lock the run

Timebox planning to roughly 10-15 minutes unless Zach wants a deeper discussion.

- Brainstorm improvement areas and new systems, not just a list of tiny fixes.
- Use `$research-coverage` when the direction depends on current tools, models, literature, or unexplored approaches.
- Separate Zach-owned choices from decisions he has delegated. If he says "make it great," own the design.
- Ask all taste forks and all destructive, financial, account, privacy/security, credential, irreversible, deployment/push, or message-sending permissions before he leaves.
- End any questions with "anything else to add?".

Produce one compact execution plan containing:

- target outcomes and non-goals;
- lane/dependency map;
- exact model, effort/mode, folder/worktree for every lane;
- acceptance criteria and quality rubric;
- test/build/live-use gates;
- permissions and external blockers;
- expected morning evidence.

If Zach also invokes `$build-sprint`, let overnight own this preflight and morning framing while build-sprint owns critical-path backlog ordering. Do not create duplicate goals, ledgers, or question sets.

Wait for confirmation unless Zach already explicitly approved this exact plan. On confirmation, update the goal to the locked outcome and put every item on the active board.

## Phase 2 - delegate automatically

Invoke `$delegate`; do not make Zach manually launch sessions.

- Dispatch all independent lanes early.
- Root stays on the deep tier at high/max effort in whichever tool Zach opened; use a parallelism-heavy root mode only when native parallel decomposition materially helps.
- Route balanced research/implementation/review to Terra high/xhigh.
- Route fully specified mechanical work to Luna medium/high.
- Use Cursor Auto/Composer or a verified specialist model for pre-scoped in-editor work.
- Use Claude only when a current verified advantage justifies it.
- Never place two editing agents in one checkout.

Every lane receives a complete packet and appears in the outstanding-work ledger with task/process ID, model, effort, folder, branch, state, acceptance, and next check.

If Zach explicitly asks for real Codex, Cursor, or Claude sessions, launch the beneficial sessions after their required confirmation rather than leaving paste-ready prompts. Verify desktop and CLI authentication separately, and do not count queued worktree setup, a staged prompt, or a sent-but-unmonitored request as running work.

## Phase 3 - execute in waves

Typical wave:

1. research/state verification;
2. implementation;
3. automated checks;
4. independent/adversarial review;
5. corrective feedback and repair;
6. integration checks;
7. live app use;
8. re-fix and re-audit.

Do not wait idly on one lane if safe useful work remains. Monitor every dispatched worker to a terminal result. Empty/truncated output, usage limits, permission prompts, auth errors, or "sent" status are not completion. Reprompt drift, reroute a failed lane, or recover from its task/thread/process state.

## Phase 4 - Cursor GUI lane

On this Windows machine, assume the Cursor GUI path unless a fresh `cursor-agent` check proves headless support.

1. Open the exact isolated folder with `cursor -n "C:\absolute\worktree"`.
2. Use live computer control to verify the folder/window.
3. Open Agent, inspect the current model roster, select the intended model and available effort/mode, and paste the packet.
4. Cursor has broad routine execution permissions; monitor permission prompts and visible progress. The packet must prohibit secrets, destructive actions, pushes, deployments, purchases, and external messages unless separately authorized.
5. Inspect the resulting diff from Codex, run verification independently, and reprompt Cursor with concrete failures when needed.

Do not infer headless Cursor support from executable discovery. Use the verified GUI path until the runner can enforce exact Cursor model and effort routing.

## Phase 5 - use the actual product

When planned code/research waves reach a candidate result, invoke `$codexaudit` and use live Windows computer control. This is mandatory for touched user-facing apps unless the app cannot run for a documented external reason.

- Launch the actual app/deployment; use Edge for visible browser work by default.
- Traverse the changed flows and adjacent obvious flows as a skeptical user.
- Try realistic inputs, empty/error/loading states, dead buttons, navigation, data truthfulness, layout, copy, and relevant mobile widths.
- Capture findings/evidence in the repo's QA location or the active board.
- Fix confirmed failures, rerun automated gates, then re-audit.

Do not stop after one click-through. Continue until acceptance criteria pass or a genuine unauthorized/external blocker remains.

## Phase 6 - morning closure

Before producing the Read-Me:

1. Reconcile the original Zach message line-by-line with the active obligation ledger.
2. Ensure every dispatched lane is terminal and every artifact is reviewed.
3. Record commits/tests/runtime observations/screenshots/task IDs as appropriate.
4. Update the board: verified items get dated evidence; waiting items get owner + trigger; obsolete items get a reason.
5. Capture durable decisions in native memory/Markdown without recording proposals as decisions.
6. Close the Codex goal only if the full objective is achieved.

The morning response contains exactly one self-contained Read-Me (Status / Questions / Suggestions) and only the genuine items Zach must decide or authorize. Do not create a vanity report, and do not emit the Read-Me while any dispatched work is non-terminal.

## Safety and recovery

- Zach's overnight authorization permits routine computer control; it does not authorize destructive, financial, account, privacy/security, credential, irreversible, deployment/push, or message-sending actions that were not explicitly approved.
- Do not expose or relocate secrets. Read the established secrets index first.
- If a model/tool changes or disappears, verify the current roster and reroute; never cling to a stale table.
- If interrupted, resume from the goal, board, task/thread IDs, git state, logs, and artifacts. Re-verify old "done/running/deployed" claims.
