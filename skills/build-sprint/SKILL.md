# Build Sprint

Turn the named request, actionable board items, and any verified unfinished candidates found in relevant memory or durable intent into an impact-ordered, dependency-aware execution plan. Keep this session responsible for integration and final acceptance.

## Compose the mode

- Standalone: Zach remains available. Continue safe work and stop only at a real decision or sensitive-action boundary.
- With `$autonomy`: let autonomy own the deadline, permissions, interruption, and unattended lifecycle; own scope, critical-path ordering, and execution pressure here.
- With `$overnight`: let overnight own the evening preflight and morning closure; use this skill to compress the authorized backlog into execution waves.
- Do not ask the same question twice or create a second competing goal/ledger.

## Scope and ordering

1. Read `~/workspace/ORCHESTRATION-BOARD.md`, relevant project instructions, task artifacts, repository state, dirty-checkout status, and active workers. Audit relevant native memory and durable intent for unfinished candidates; verify each against current evidence and promote only genuinely actionable unresolved items onto the board before execution. Memory supplies leads, never the active queue. If no candidate is actionable, record the checked state without inventing work. Enumerate every ask, aside, constraint, and future item.
2. Separate actionable, waiting, obsolete, and Zach-owned items. Rank by user impact, critical-path unblock, risk, reversibility, and effort. Resolve real decisions first; if paired with `$autonomy` or `$overnight`, batch all required questions before departure.
3. Define observable acceptance criteria, verification gates, next triggers, and closure evidence for every item. Execute from the reconciled board, never directly from memory.

## Execute in isolated lanes

1. Preserve dirty checkouts and user work. Use isolated worktrees or disjoint folders; never let two editing workers share a checkout.
2. Invoke `$delegate` for three or more independent lanes, a large context dump, or work likely to exceed an hour. Give each lane a complete packet with exact current model, effort/mode, folder/worktree, scope exclusions, acceptance, and evidence requirements.
3. Keep root ownership of architecture, taste, integration, prioritization, and final judgment. Monitor every worker to a terminal state, inspect its actual diff/output, and correct drift or failures before integration.

## Quality loop

1. Run relevant tests, static checks, builds, and data checks. Inspect the diff for unrelated or accidental edits.
2. Perform an adversarial review against the acceptance criteria and adjacent obvious failure modes. Repair confirmed defects across the affected class.
3. Invoke `$codexaudit` for user-facing changes. Use the actual app or workflow with live computer control, exercise changed and adjacent paths, and record observed evidence. Prefer Microsoft Edge for visible browser QA.
4. Rerun automated checks and the live audit after repairs. Mark an item verified only when its acceptance criteria and evidence are observed.

## Close or wait durably

Reconcile the original request line by line before reporting. Update the board with verified status, owner/lane, exact model and effort/folder for delegated work, next trigger, acceptance, and closure evidence. For waiting items, name the blocker and resume trigger. "Dispatched," "build passed," and "saved to memory" are not completion. Do not claim closure while any worker or integration result remains unreviewed.
